# 2026.322.0202 — fix(jupyter-ml): pin layer-cuda to the version the boxes declare

## Summary of changes

`charly.yml` gains one changed line: the `layer-cuda` requirement moves from
`v2026.290.1513` to `v2026.321.1520`.

Diff, from `git diff --numstat origin/main...HEAD`:

```text
1     1   charly.yml
```

**Why.** `box/nvidia` and `box/versa` in `distro-cachyos` both pin
`layer-cuda:v2026.321.1520`. This candy pinned `v2026.290.1513`. Composed into either box, one
scope then holds two `layer-cuda` tags with differing content and charly refuses to choose:

```text
validation error: candy layer-cuda resolved to multiple git tags with differing content within
one scope (box=versa); using newest referenced v2026.321.1520;
also referenced v2026.290.1513; also referenced v2026.314.0705
```

That is pre-existing and red repo-wide, so no PR in `distro-cachyos` can reach a clean gate
(opencharly/distro-cachyos#197).

**Scope.** One requirement line. No package, plan step, service or check changes; the candy's
behaviour is identical, it simply names the same `layer-cuda` version its consumers already use.

## How tested

The edit is a pin, so the two things that can be checked in this repo are that the named tag
exists, and that the candy still parses. Both, run in the branch's checkout:

```text
$ git ls-remote --tags https://github.com/opencharly/layer-cuda.git | grep 'v2026.321.1520'
d8160f282e203353a9b0831abd5705f8d84016ba	refs/tags/v2026.321.1520

$ python3 -c "import yaml; yaml.safe_load(open('charly.yml'))"
(no output)
exit=0

$ grep -n 'layer-cuda' charly.yml
15:            - '@github.com/opencharly/layer-cuda:v2026.321.1520'
```

`yaml.safe_load` prints nothing on success — the earlier revision of this body showed `YAML OK`
beside that command, which the command does not emit; the `exit=0` above is what it actually
produces.

**What is not proven here.** The end-to-end proof — `charly box validate` reporting 0 warnings on
a `distro-cachyos` tree that composes this candy — cannot be produced from this repo alone. It
needs this PR *and* the sibling pins in `layer-python-ml` and `pod-unsloth-studio` merged, and then
the three pins advanced in `distro-cachyos`. That sequencing is recorded in
opencharly/distro-cachyos#197, and until it completes this PR is `analysed on a live system` rather
than `fully tested and validated`.
